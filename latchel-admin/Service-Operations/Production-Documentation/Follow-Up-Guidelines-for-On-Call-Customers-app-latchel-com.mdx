## 🧠 What This Process Is Trying to Solve

<Note>
  We want to prevent missed follow-ups, confusion, and inconsistent communication when residents or service providers reach out about their work orders under the On-Call program. The goal is to provide a clear, step-by-step process for associates to handle follow-up questions via SMS, calls, or email—ensuring every inquiry is acknowledged, properly documented, and escalated to the right party (like the Property Manager) when needed.
</Note>

<Warning>
  ### **🚨 New On‑Call Alerts – Limited Customers Only**

  We are rolling out a new **On‑Call Alerts** model. This applies to properties that have the **On-Call add-on** enabled. To confirm if a property is on this model, navigate to the property page in [app.latchel.com](http://app.latchel.com/) and check the **Addon** field — it should display **"On-Call"**.
</Warning>

## 📋 Step-by-Step Process

<Warning>
  ### 🔄 Calling Policy (On‑Call Follow‑ups)

  **Do not place outbound calls to residents, Property Managers, or Service Providers for On‑Call follow‑ups. Use SMS/email and the Response Links in app.latchel.com.**<br />**Exception: The Need to Verify (NTV) workflow may require an outbound call to the resident as described in the Handling “Need to Verify” Inquiries section.**

  **When a PM or On-Call Technician Contacts Us**

  - **Treat the caller (reporting party) like a resident and follow the standard resident-reported intake/on-call workflow.**
  - **If changes are needed, submit a new WO/alert through the normal process, just as you would for resident inquiries.**
  - **This applies even if a different technician may be dispatched for the new WO/alert.**
  - **When submitting a new work order or on-call alert, choose/select the primary resident associated with the property.**
  - **Always document the reason for creating/submitting a new work order/alert and who contacted us (inbound).**
</Warning>

### 1️⃣ Where Ops should look for On-Call Alerts

When a **resident** or **service provider** or **PM** from an on-call customer follows up about an on-call issue:

1. **Search for a work order as you normally would.**
2. **If no work order is found for the issue:**
3. Confirm that the PM company is an on-call customer.
4. Go to the **PM, portfolio, property, or resident** view in `http://app.latchel.com`.
5. Click the **On-Call Alerts** tab (next to the **Maintenance** tab).

<Frame>
  ![image-20260112-202351.png](/images/SVC-891.png)
</Frame>

4. Look for the relevant alert (use resident name, property, and recent date/time to identify it).

> **Note:** There is **no dedicated search** inside the On-Call Alerts tab yet, and On-Call Alerts are **not included in global search**. We plan to add this. For now, Ops may need to visually scan the alerts list to find the correct one.

### 2️⃣ How to respond when an On-Call Alert exists

When you open the On-Call Alert:

1. **Check the current Status** of the alert.
2. \*\*Refer to \*\*[https://help.latchel.com/latchel-admin/Service-Operations/Production-Documentation/Follow-Up-Guidelines-for-On-Call-Customers-app-latchel-com](https://help.latchel.com/latchel-admin/Service-Operations/Production-Documentation/Follow-Up-Guidelines-for-On-Call-Customers-app-latchel-com).
3. **Use the Response Link for follow-ups:**
4. Vendors (on-call techs), backup contacts (PMs), and residents receive a **response link by SMS/email** when the alert is created or updated.
5. To access the response links and use them when a customer makes a follow-up, open the **On-Call Alert Details**.
6. Once opened, you will see sections for **Vendor**, **Backup Contact**, and **Resident**, each with a response link below it. Use the appropriate response link depending on who is making the follow-up.

<Frame>
  ![image-20260113-175641.png](/images/SVC-892.png)
</Frame>

2. **For follow-up questions**, Ops should:
3. Inform the caller of the **current Status** of the alert, and
4. **Copy/paste or re-send the Response Link** so they can review or take the appropriate action on their side.
5. **Say something like:** _“Hi \[Customer Name\], thanks for reaching out. The current status of your request is **\[Status\]**. You may have received a link to view updates before, but I’m sending it again so you can quickly see the latest details and take any action if needed: \[Insert Response Link\].”_
6. \*\*If the resident says the issue has gotten worse, reoccurred or not resolved \*\* and the alert is in **Successful, Escalated, or Cancelled**:
7. Advise that they (or Ops on their behalf) can **submit a new request**.
8. If the intake session matches to a “Go On Call Outcome,” this will create a **new On-Call Alert** and the on-call tech will be alerted again.
9. **Say something like:** _“I understand the problem has (gotten worse, reoccurred, not resolved). Since this request is already **\[Completed / Escalated / Cancelled\]**, we’ll need to create a new request. You can submit it using this link **\[insert the link to the resident’s public dashboard\]**, or I can create it for you. Once it’s submitted, the tech will be notified and will contact you.”_
10. If the resident chooses to submit the request themselves, no further action is needed.
11. If the resident asks for assistance and wants you to submit the request on their behalf, go ahead and submit it (this applies to calls and emails only). For requests received via SMS, follow our standard process and direct the resident to submit the maintenance request themselves.
12. **Tasks for PMs:**

- For these On-Call Alerts, **Ops will not create tasks for PMs on the alert itself**.
- Continue to follow existing PM communication and task-management guidelines for all other PM-related concerns.

<Accordion title="Q14: What should we do if the call center or tenant submission flow is down for an on-call customer?">
  **A:** Use this process when you are unable to submit a WO through the normal call center flow (`app.latchel.com/call-center/handle-call`) or tenant flow for an **on-call customer**.

  **First, check if the issue is on your end:**

  | Try This | Notes |
  | --- | --- |
  | Hard refresh (Ctrl\+Shift\+R / Cmd\+Shift\+R) | Clears cached state |
  | Close and re-open the page | Resolves session-related errors |
  | Clear browser cache and cookies | [Instructions](https://support.google.com/accounts/answer/32050) |
  | Try the tenant flow as a fallback | Runs on a separate system |

  **If the issue persists, check with Support** to see if they are able to submit on your behalf before proceeding with the Console workaround.

  If Support is also unable to submit, proceed with the steps below.

  **Step 1 — While the resident is still on the phone**

  1. **Do not end the call.** Keep the resident on the line and complete the full diagnostic verbally. Gather all information normally collected during intake, including the issue description/severity, Permission to Enter (PTE), availability, and contact number.
  2. **Submit the WO via Console/property profile** as a temporary workaround so the request is documented.
  3. Inform the resident: _“I’ve submitted your request. You’ll be hearing from us shortly with next steps.”_

  **Step 2 — Notify Support**

  Notify Support immediately after submitting the WO via Console/property profile.

  - **Important:** Submitting via Console/property profile skips all on-call dispatch logic. Support needs to track these WOs for resubmission once the tech issue is resolved.
  - Include the WO number, property address, and a note that it was submitted via Console/property profile due to a system outage.

  **Step 3 — After the tech issue is fixed**

  Once Engineering confirms the call center/tenant flow is restored, **Support owns the resubmission process** for affected on-call customer WOs.

  1. **Support resubmits the WO** through the normal call center or tenant flow so the on-call dispatch logic is triggered.
  2. Diagnostics were already completed in Step 1, so the resident does not need to be called back unless required for missing information.
  3. **Support cancels the original Console/property profile WO** and adds a cancellation note.

  **Cancellation note:**

  > _Cancelled — resubmitted via call center flow on \[date\] after system outage. Original WO was submitted via Console/property profile as a workaround. On-call dispatch logic applied via resubmission._

  **Key reminders**

  - Never resubmit before Engineering confirms the fix is live.
  - Console/property profile submission skips on-call dispatch logic, so Support must resubmit through the normal flow after the fix.
  - Support must be notified any time a WO for an on-call customer is submitted via Console/property profile during an outage.
</Accordion>
